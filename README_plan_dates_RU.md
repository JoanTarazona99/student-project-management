# Изменение дат утвержденного плана (расширение ФЗ-05)

Первая версия изменяет только `starts_at` и `due_at` существующих этапов.
Добавление, удаление, переименование, изменение порядка и новый процесс
предложений/голосования не реализованы. Контракт endpoint и механизм ожидаемых
дат — решения этой реализации, не дословные требования преподавателя.

## Endpoint и пример

`PUT /projects/{project_id}/plan/dates`, Bearer JWT. Ответ — тот же полный
план, что возвращает `GET /projects/{project_id}/plan`, с сохраненными ID,
позициями, названиями, статусами и исходными полями утверждения.

Сначала получите план. Отправьте **ровно все** его этапы, включая завершенные.
ID ниже иллюстративны: используйте ID из GET, не предполагайте их значения.
Пример целого плана из трех этапов: первый уже completed и остается неизменным,
срок второго увеличивается, начало третьего согласуется с новым сроком второго.

```http
PUT /projects/100/plan/dates
Authorization: Bearer <ваш токен>
Content-Type: application/json

{
  "reason": "Уточнение сроков по согласованию с руководителем.",
  "stages": [
    {
      "stage_id": 201,
      "expected_starts_at": "2026-10-01T00:00:00+03:00",
      "expected_due_at": "2026-10-10T00:00:00+03:00",
      "starts_at": "2026-10-01T00:00:00+03:00",
      "due_at": "2026-10-10T00:00:00+03:00"
    },
    {
      "stage_id": 202,
      "expected_starts_at": "2026-10-10T00:00:00+03:00",
      "expected_due_at": "2026-10-20T00:00:00+03:00",
      "starts_at": "2026-10-10T00:00:00+03:00",
      "due_at": "2026-10-22T00:00:00+03:00"
    },
    {
      "stage_id": 203,
      "expected_starts_at": "2026-10-20T00:00:00+03:00",
      "expected_due_at": "2026-10-31T00:00:00+03:00",
      "starts_at": "2026-10-22T00:00:00+03:00",
      "due_at": "2026-10-31T00:00:00+03:00"
    }
  ]
}
```

Все даты обязательны и должны иметь часовой пояс; они нормализуются в UTC.
Эквивалентные offsets сравниваются как одинаковые моменты.
`project_id`/`stage_id` — положительный bigint от 1 до 9223372036854775807.
`reason` после strip: 10–2000 символов; список: 1–50 элементов, без повторов ID.
Неизвестные поля запрещены на обоих уровнях.

## Авторизация и правила

Нужны активная учетная запись, разрешение `plans.approve` и текущее назначение
как supervisor_id или teacher_id. Студент проекта никогда не разрешает
собственный перенос, даже при нескольких ролях и наличии plans.approve.
Student, department и admin со штатными разрешениями не имеют доступа.
Начальная матрица разрешений не меняется.

- Без токена/при неактивном аккаунте в начальной аутентификации: 401.
- Нет разрешения или назначенных полномочий, в том числе автоавторизация: 403.
- Несуществующий/чужой проект: 404, согласно прежнему PROJECT_SCOPE.
- Plan не утвержден, отсутствуют этапы или все completed: 409.
- Неверный набор ID (лишние, недостающие, неизвестные или чужие): 422 с общим
  сообщением, без сведений о принадлежности другого этапа.
- Структурная ошибка тела, временного интервала или пересечение: 422.
- Ожидаемые даты устарели или меняются даты completed: 409.
- Ошибка/timeout БД: прежний безопасный ответ 503; изменения откатываются.

По каждому этапу `due_at > starts_at`. По порядку **stages.position** начало
следующего не раньше срока предыдущего. Порядок массива клиента не важен.
Даты completed неизменны, но такой этап обязательно включается в запрос.
Остальные статусы (planned, in_progress, under_review, revision) могут менять
даты даже при наличии материалов и непроверенной версии.

Прошедшие даты разрешены при структурно корректном плане. Достижение даты не
закрывает этап, не отменяет проверку и не изменяет прогресс. Этапы не удаляются
и не заменяются; материалы, ревизии, файлы и completed_at сохраняются.
Первоначальные plan_approved_at/plan_approved_by не изменяются. Первоначальная
`PUT /plan` по-прежнему возвращает 409 для утвержденного плана.

## Ожидаемые даты и конкурентные запросы

Транзакция `READ COMMITTED`: сначала проект `FOR UPDATE` через существующий
scope, затем все его этапы `FOR UPDATE` в порядке ID. Для проверки соседства
этапы сортируются по position. Тот же порядок «проект → этапы» соблюдают
планирование, материалы/принятие и генератор сроков.
Административный advisory lock не используется.

После ожидания блокировок перечитываются актуальные даты/статусы. Активность и
plans.approve actor повторно проверяются существующим helper
`require_current_actor`; его административный lock не вызывается.
Назначение берется из заблокированной текущей строки проекта, студент
исключается явно. Если назначение было снято до получения lock, scope может
дать 404; при утрате активности/разрешения после начальной аутентификации — 403.

Оба expected-поля **каждого** этапа сравниваются с текущими значениями до любых
UPDATE. Любое несовпадение отклоняет весь запрос с 409. Нет частично измененных
планов. Если принятие завершило этап первым, его даты теперь неизменны:
попытка переноса отклоняется. Если изменение дат подтверждено первым,
ожидающее принятие проверяет материал по прежним академическим правилам,
с новым сроком; состояние/прогресс сам перенос не меняет.

Рекомендуемый порядок после 409: повторный GET, просмотр актуального состояния,
согласование новых дат, новый запрос с текущими expected-полями.
Ожидаемые даты — сравнение значений, не полная версия плана: изменение и
возврат к тем же датам между GET и PUT (ABA) не распознается. Новых таблиц
версий или idempotency keys нет.

Актуальный no-op возвращает 200 без аудита/уведомлений. Повтор исходного
изменяющего запроса после успеха обычно возвращает 409: его expected устарели.
Новый запрос с актуальными expected и неизменными новыми датами — no-op.
Для полностью завершенного проекта действует 409 даже при no-op.

Timeout только новой операции: lock 5 с, statement 30 с, transaction 60 с
(PostgreSQL 17). Начальная аутентификация и существующие endpoints сохраняют
прежние настройки. Ошибки подтверждения не дают частичной транзакции;
при сетевом обрыве около COMMIT клиенту следует перечитать план и аудит,
не предполагать, что запрос точно не был применен.

Граница авторизации — повторная проверка внутри транзакции после блокировки
этапов. Роли/аккаунты дополнительно не блокируются; изменение разрешений или
активности после этой проверки не отзывает ретроактивно запрос. Нельзя обещать
постоянное разрешение до ответа или ревокацию уже разрешенной операции.

## Аудит и уведомления

Один `audit_events` с action `plan_dates_changed`, actor, entity `projects`,
project_id. Details: project_id, reason после strip, changed_at UTC (время БД
после UPDATE), operation_id UUID, список **только измененных** stage_id/position
и before/after с UTC ISO 8601, шестью микросекундами и `Z`.
Это отдельная история, не повтор первоначального утверждения.

В той же транзакции создаются русские уведомления студенту, руководителю
и преподавателю: уникальные активные ID, без actor. Активность адресатов
читается самим INSERT SELECT после аудита. Неактивные назначения не заменяются.
Ключ `plan-dates-changed:<UUID>` (<200 символов), UUID общий с audit details.
Номер изменения не вычисляется через COUNT. Предыдущие события и read_at
не изменяются. Отказ/rollback не оставляет ни даты, ни аудит, ни уведомления.
Нет паролей, JWT, DSN или содержимого файлов в событиях.

## Отчеты, состояние и временные уведомления

GET плана и состояния читают новые даты. Прогресс и статус прежние;
overdue использует актуальный due_at и прежнее строгое сравнение.
Отчет также пересчитывает overdue, без изменения его фильтров/контракта.

Генератор не вызывается из endpoint. В следующем добровольном запуске он
блокирует проект и видит подтвержденные даты. Если генератор первым получает
lock, он вправе сохранить уведомления прежнего срока до ожидающего переноса:
это история, не удаляемая переносом. Новый due_at имеет новый ключ срока.
Изменение только starts_at не повторяет уведомление для прежнего due_at.
См. [README_deadlines_RU.md](./README_deadlines_RU.md).

## Проверки и ограничения

См. [README_tests_RU.md](./README_tests_RU.md). Только PostgreSQL, созданный
fixtures, временное хранилище, динамические ID и настоящая авторизация.
Рабочий `.env`, PostgreSQL и `uploads/` не используются.
Глобальный генератор в новых сценариях изолируется временным исключением
утверждений прежних тестовых проектов с обязательным восстановлением в finally.
Тест, временно меняющий общую связь разрешений, также восстанавливает ее.

```powershell
.\.venv\Scripts\python.exe -m scripts.test_materials_unit
.\.venv\Scripts\python.exe -m pytest tests -v --postgres-backend=native --pg-bin="C:\Program Files\PostgreSQL\17\bin"
.\.venv\Scripts\python.exe -m pytest tests -v --reverse-order --postgres-backend=native --pg-bin="C:\Program Files\PostgreSQL\17\bin"
.\.venv\Scripts\python.exe -m pip check
git diff --check
```

CI уже обнаруживает новый модуль через `pytest tests`; workflow, зависимости,
схема, роли и начальная матрица не меняются. Проверяются доступ, текущие
expected, структура, completed, сохранение материалов/файлов, аудит/уведомления,
rollback, оба порядка гонок с принятием/сроками и повторная авторизация после
наблюдаемого ожидания реального блокирования. Предыдущие assertions сохранены.

Не покрыты сеть непосредственно при COMMIT, crash recovery, нагрузка,
ABA и отмена разрешения после повторной проверки. Отдельной истории версий
плана, изменения состава/названий/порядка этапов и нового процесса согласования
нет. Ничего не планируется в Task Scheduler, merge и deployment не выполняются.
Это не подтверждение готовности к production: остаются ограничения загрузок
и координации PostgreSQL/файловой системы.
