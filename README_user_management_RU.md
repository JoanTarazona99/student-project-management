# Управление учетными записями

Административные операции ФЗ-01 позволяют частично изменить основные данные
пользователя и включить или отключить его учетную запись. Управление ролями,
паролями и удаление пользователей в этот API не входят.

## API и доступ

Обе операции требуют действующий JWT и разрешение `users.manage`:

```http
PATCH /admin/users/123
Authorization: Bearer <token>
Content-Type: application/json

{"first_name": "Анна", "middle_name": null}
```

```http
PATCH /admin/users/123/status
Authorization: Bearer <token>
Content-Type: application/json

{"is_active": false}
```

Ответом служит `UserSummary`: ID, email, имя, фамилия, отчество, учебная
группа, состояние и коды ролей. Пароль, его хеш и JWT в ответ не включаются.
Без токена возвращается 401, без `users.manage` — 403, если пользователь не
найден — 404, при конфликте email или последнего администратора — 409,
при неверном запросе — 422. ID должен быть положительным числом в диапазоне
bigint PostgreSQL.

## Редактирование

`PATCH /admin/users/{user_id}` принимает только `email`, `first_name`,
`last_name`, `middle_name` и `study_group`. Неизвестные поля, в том числе
роли и пароль, отклоняются с 422. Непереданные поля сохраняются; запрос без
полей также получает 422. Email, имя и фамилия обязательны и не могут быть
`null` или пустыми. Email обрезается по краям и приводится к нижнему регистру;
уникальность нечувствительна к регистру. `middle_name` и `study_group` можно
очистить значением `null`.

Редактирование активной или отключенной учетной записи не меняет ее роли и
связи с проектами. Конфликт email не оставляет частичного обновления.
Нормализованный запрос без фактических изменений возвращает текущее состояние
без нового события аудита.

## Активация и защита администраторов

`PATCH /admin/users/{user_id}/status` принимает только JSON boolean
`is_active`. Строки, числа и `null` не являются допустимыми значениями.
Повторная установка текущего состояния возвращает 200 и не создает событие
аудита.

Отключенная учетная запись не может войти в систему; ранее выданный JWT также
не проходит проверку, поскольку приложение проверяет активность пользователя
на каждом запросе. После повторной активации вход разрешен, и еще не истекший
JWT снова проходит проверку. Постоянного отзыва JWT в системе нет.

Администратор не может отключить собственную учетную запись. Последнего
активного пользователя с ролью `admin` отключить нельзя. Проверка выполняется
в транзакции: строка целевой учетной записи блокируется `FOR UPDATE`, а
изменения активности администраторов сериализуются общим транзакционным
PostgreSQL advisory lock перед подсчетом активных администраторов. Так два
одновременных запроса не могут оба отключить последнего администратора.
Отклоненный запрос не блокирует строки других учетных записей.

Отключение не удаляет проекты, этапы, материалы, ревизии, уведомления, роли
или аудит. Пользователь может продолжать отображаться в проекте как ранее
назначенный или ответственный участник; автоматического переназначения нет.

## Аудит

Каждое фактическое изменение данных или состояния и соответствующее событие
`public.audit_events` фиксируются в одной транзакции. Событие содержит актера,
действие, целевую учетную запись и измененные поля с прежними и новыми
значениями. Отклоненный запрос и повтор без изменений не добавляют событие.
Пароли, хеши, JWT, данные подключения и заголовки авторизации в детали аудита
не записываются. Уведомления этими операциями не создаются.

## Запуск тестов

Требуются Python 3.13, зависимости из `requirements-test.txt` и Docker с
Linux-контейнерами либо установленные PostgreSQL 17 `initdb` и `postgres`.
Из корня репозитория:

```console
python -m pip install -r requirements-test.txt
python -m scripts.test_materials_unit
python -m pytest tests -v --postgres-backend=docker
```

В Windows без Docker можно указать каталог бинарных файлов PostgreSQL:

```console
python -m pytest tests -v --postgres-backend=native --pg-bin="C:\Program Files\PostgreSQL\17\bin"
```

Fixture запускает собственный PostgreSQL-сервер в контейнере или временном
кластере, использует случайные пароль БД и `JWT_SECRET`, создает базу и
пользователей только в этом сервере и применяет исходную SQL-схему без
изменений. Настоящий `.env`, рабочая БД и `uploads/` не используются;
загрузка материалов изолирована во временном каталоге. В GitHub Actions те же
две команды выполняются workflow `Backend tests`; секреты пользователя не
требуются. Если Docker или PostgreSQL отсутствует, интеграционные тесты
завершаются ошибкой, а не пропускаются.

## Ограничения

Набор проверяет API учетных записей и конкурентную защиту последнего
администратора, но не управление ролями, отзыв JWT, отказы диска или
PostgreSQL и согласованность PostgreSQL с файловой системой при аварии.
Проверки не являются подтверждением готовности системы к эксплуатации в
production.
