# Внутренние уведомления о сроках (ФЗ-08)

Разовый обход PostgreSQL 17; HTTP endpoint, сервис и scheduler не добавлены.
Команда ничего не отправляет во внешние системы.

## Запуск

Нужны Python и зависимости существующего backend, PostgreSQL 17 и заполненная
штатная конфигурация подключения `.env` в корне проекта:
`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`.
Используется прежний загрузчик `app.database`, без изменения приоритета
настроек. JWT для команды не нужен. Конфигурация читается только после
проверки аргументов; `--help` и ошибки аргументов не подключаются к БД.

Из корня репозитория, с Python виртуального окружения:

```powershell
.\.venv\Scripts\python.exe -m scripts.check_deadlines
.\.venv\Scripts\python.exe -m scripts.check_deadlines --dry-run --warning-hours 24
.\.venv\Scripts\python.exe -m scripts.check_deadlines --apply --warning-hours 24
```

По умолчанию выполняется **симуляция**, не применение. `--dry-run` и `--apply`
взаимоисключающие. `--warning-hours`: целое число 1–168, по умолчанию 24.
24 часа — конфигурируемое решение реализации, не требование преподавателя.
Некорректные аргументы завершаются с кодом 2. Ошибки конфигурации/БД — с кодом 1;
успешный обход — с кодом 0.

Применение к рабочей БД допускается только при добровольном запуске оператором.
При разработке и проверке команда использовалась только с конфигурацией
одноразового сервера; рабочие `.env`, БД и `uploads/` не использовались.

## Время и адресаты

Один `reference_time` UTC фиксируется до начала обхода. Программа не меняет
часы системы. Времена с разными offsets сравниваются как моменты UTC.

- Рассматриваются этапы проектов с утвержденным планом.
- `planned`, `in_progress`, `under_review`, `revision` допускают уведомления.
- Приближающийся срок: `reference_time < due_at <= reference_time + окно`.
- Истекший срок: `reference_time > due_at`.
- При точном равенстве уведомления обоих видов отсутствуют.
- `completed` не уведомляется даже при позднем завершении.
- Проекты без этапов или утверждения плана не генерируют уведомлений.

Получатели: студент, назначенный руководитель (если есть), назначенный
преподаватель. Повторяющийся ID учитывается один раз. Неактивные аккаунты
исключаются без переназначения ответственности. Администраторы, кафедра и
чужие проекты не получают глобальных уведомлений. Роли не переоцениваются:
используются именно назначения проекта и активность аккаунта.

Русское сообщение содержит номер проекта, название и номер этапа, срок UTC.
Команда выводит только счетчики и диагностические ID, не имена, email,
материалы, внутренние пути, пароли или JWT.

## Дедупликация и аудит

Ключ: `deadline:<upcoming|overdue>:<stage_id>:<due_at_utc>`.
`due_at_utc` нормализуется в UTC, ISO 8601 с шестью цифрами микросекунд и `Z`,
например `2035-05-10T13:00:00.000000Z`. ID — десятичный bigint.
Ключ детерминирован и короче 200 символов даже для максимального bigint;
хеширование не используется.

Уникальность `(recipient_id, event_key)` обеспечивается прежней SQL-схемой.
Применение использует `INSERT ... ON CONFLICT DO NOTHING RETURNING id`;
счетчики отражают только возвращенные, фактически вставленные записи.
Нет пары «проверить отсутствие, затем вставить» в режиме применения.
Изменение окна не повторяет прежний близкий срок. Новый срок имеет другой ключ;
близкий и истекший срок — отдельные события. История и `read_at` сохраняются.

Один аудит `deadline_notifications_generated` на этап и вид уведомления,
только если вставлены новые записи. `actor_id = null`, сущность `stages`;
details содержат проект, этап, вид, срок UTC, reference_time, количество и ID
новых уведомлений. Аудит и уведомления подтверждаются одной транзакцией.
Повтор без новых записей не создает аудит или уведомления.

## Транзакции, блокировки и граница согласованности

Сначала читается упорядоченный список ID всех проектов. Проекты, созданные
после этого чтения, попадут в следующий запуск. Каждый проект обрабатывается
отдельной транзакцией, в возрастающем порядке ID.

Применение: `READ COMMITTED`, сначала строка проекта `FOR UPDATE`, затем его
этапы `FOR UPDATE` в порядке ID. Планирование, замена предложения и проверка
материалов уже блокируют проект перед этапами. Общий административный advisory
lock не используется. После получения блокировки заново читаются утверждение,
принадлежность этапов, статус и актуальный срок; старый список этапов не хранится.
Будущие операции изменения дат должны соблюдать тот же порядок «проект → этапы».

Активность всех уникальных адресатов читается одним запросом после блокировки
этапов. Это граница видимости активности аккаунтов; изменение активности после
этого чтения не отзывает уже выбранный набор. Строки пользователей и роли
дополнительно не блокируются, чтобы не вводить обратный порядок блокировок
с административными действиями.

Подтвержденное завершение до обработки проекта исключает уведомление.
Если генератор первым удерживает проект, он может подтвердить уведомление до
ожидающей проверки; последующее принятие этапа не удаляет уведомление.
Весь обход не является глобальным snapshot: один момент времени, но отдельная
согласованная обработка каждого проекта.

Симуляция: отдельный `REPEATABLE READ READ ONLY` snapshot на проект, без
блокировок строк и записей, включая аудит. Показанные кандидаты не резервируются
и могут отличаться от последующего применения.

Лимиты PostgreSQL на проект: `lock_timeout = 5 секунд`,
`statement_timeout = 30 секунд`, `transaction_timeout = 60 секунд`
(последний требует PostgreSQL 17). Чтение исходного списка ограничено 30 секундами.
Штатное подключение имеет `connect_timeout = 5 секунд`.
Нет ожидания следующего интервала внутри транзакции: обход завершается.
Общее время зависит от числа проектов; это не жесткий timeout всего процесса.

## Счетчики и ошибки

- Проектов рассмотрено: попытки обработки ID из начального списка.
- Этапов рассмотрено: все этапы утвержденных проектов в успешных транзакциях,
  включая completed и находящиеся вне окна; неутвержденные проекты дают 0.
- Близкие/истекшие: новые кандидаты в симуляции, вставки в применении,
  единица измерения — уведомление конкретному получателю.
- Уже существующие: конфликтующие пары ключ/активный получатель
  для текущих подходящих этапов; не вся историческая таблица уведомлений.
- Неактивных пропущено: число уникальных неактивных адресатов на каждый
  подходящий незавершенный этап, не число разных пользователей за весь обход.
- Успешных снимков/подтвержденных транзакций проектов и ошибок: отдельно.
  Успешный проект может не содержать новых уведомлений.

Ошибка проекта откатывает его уведомления и аудит; остальные проекты продолжают
обработку. Счетчики включают только подтвержденные транзакции/успешные snapshots.
При ошибке выводятся проект, безопасный SQLSTATE (без текста исключения/DSN),
результат транзакции и список подтвержденных проектов. Ошибка начального чтения
не запускает обработку. Любая ошибка дает ненулевой exit code.

При потере соединения около COMMIT результат может быть неизвестен: программа
не утверждает, что запись отсутствует. Требуется повторный обход после
восстановления связи; уникальные ключи защищают от повторных записей.

## Воспроизводимые проверки

См. [README_tests_RU.md](./README_tests_RU.md). Только fixture создает PostgreSQL,
случайные учетные данные и временное хранилище. Не передавайте рабочий DSN.
CLI-тесты передают конфигурацию disposable-сервера через stdin дочернему Python
и перехватывают dotenv до импорта, без чтения `.env`. Часы контролируются тестом.
Для глобального обхода новые тесты временно исключают утверждения других
сценариев на тестовом сервере и восстанавливают их в `finally`.

```powershell
.\.venv\Scripts\python.exe -m scripts.test_materials_unit
.\.venv\Scripts\python.exe -m pytest tests -v --postgres-backend=native --pg-bin="C:\Program Files\PostgreSQL\17\bin"
.\.venv\Scripts\python.exe -m pytest tests -v --reverse-order --postgres-backend=native --pg-bin="C:\Program Files\PostgreSQL\17\bin"
.\.venv\Scripts\python.exe -m pip check
git diff --check
```

`--reverse-order` — тестовая опция, разворачивающая порядок собранных cases.
CI уже запускает `pytest tests` на disposable Docker PostgreSQL, обнаруживает
новый модуль без изменения workflow и ничего не планирует на рабочей машине.
Проверяются строгие границы времени, offsets, все статусы, адресаты, повторения,
смена срока, read_at, отсутствие записей в симуляции, аудит/rollback, ошибки CLI,
ожидание блокировок и обе очередности гонки с реальным API принятия.

## Ограничения

Не проверяются сетевой обрыв непосредственно при COMMIT, перезапуск сервера,
большие объемы/производительность, будущие процедуры изменения дат и эксплуатация
Task Scheduler. Нет внешней доставки, напоминаний с повторной периодичностью,
отзыва уведомлений, глобального snapshot или гарантии остановки процесса за
фиксированное время при любом числе проектов. Момент фактической вставки может
быть позже reference_time; классификация намеренно использует единый момент.
Схема таблиц, начальные разрешения, состояния/даты этапов и прогресс не меняются.
Готовность к production не заявляется: сохраняются известные ограничения
обработки загрузок и общей атомарности PostgreSQL/файловой системы.
