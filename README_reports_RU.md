# ФЗ-09 — сводная отчетность по проектам

Первый этап отчетности предоставляет преподавателям и представителям кафедры
JSON-сводку текущего состояния проектов, этапов, прогресса и сроков. Это
решение конкретного проекта для первичной реализации ФЗ-09; перечисленные ниже
путь, формат JSON и фильтры являются проектными решениями, а не утверждением о
дословных требованиях преподавателя. Фронтенд, PDF/Excel, рассылка и фоновые
задания не входят в область этой поставки.

## Endpoint

`GET /reports/projects`

Для запроса необходим действующий JWT и разрешение `reports.read`.
Преподаватель видит только проекты, где он указан как `teacher_id`.
Представитель кафедры видит все проекты существующего общего пространства:
в схеме нет отдельной модели кафедр или связей подразделений. При наличии обеих
ролей применяется область кафедры. Наличие `projects.read`, назначение
руководителем или само разрешение `reports.read` без одной из этих ролей
недостаточно. Фильтры никогда не расширяют область доступа.

## Фильтры

Все параметры необязательны:

| Параметр | Значение |
|---|---|
| `created_from` | Дата/время с часовым поясом, включительно (`created_at >=`) |
| `created_before` | Дата/время с часовым поясом, исключительно (`created_at <`) |
| `student_id` | Положительный ID студента |
| `supervisor_id` | Положительный ID руководителя |
| `teacher_id` | Положительный ID преподавателя |
| `status` | `planning`, `in_progress`, `under_review`, `revision`, `completed` |
| `overdue_only` | Только проекты с просроченным незавершенным этапом; по умолчанию `false` |
| `limit` | Размер страницы от 1 до 100; по умолчанию 50 |
| `offset` | Смещение от 0; по умолчанию 0 |

Даты сдвигаются в UTC; время без часового пояса и интервал с `created_from >=
created_before` отклоняются с HTTP 422. Если указан только один край, второй
остается открытым. Период применяется только к `projects.created_at`, а не к
датам этапов, материалов, проверок или завершения.

Отчет показывает **текущее состояние** проектов, созданных в выбранном периоде.
Это не исторический снимок и не реконструкция состояния на `created_from` или
`created_before`. Фильтры идентификаторов вне доступа преподавателя возвращают
пустой результат без раскрытия наличия таких данных.

## Ответ

Пример сокращенного ответа:

```json
{
  "generated_at": "2026-10-31T12:00:00Z",
  "filters": {
    "access_scope": "teacher",
    "created_from": null,
    "created_before": null,
    "student_id": null,
    "supervisor_id": null,
    "teacher_id": null,
    "status": null,
    "overdue_only": false
  },
  "limit": 50,
  "offset": 0,
  "total_matching": 1,
  "summary": {
    "status_counts": {
      "planning": 0,
      "in_progress": 1,
      "under_review": 0,
      "revision": 0,
      "completed": 0
    },
    "overdue_projects": 0,
    "total_stages": 3,
    "completed_stages": 1
  },
  "items": [{
    "project_id": 42,
    "topic_id": 17,
    "topic_title": "Тема проекта",
    "student_id": 8,
    "supervisor_id": 5,
    "teacher_id": 3,
    "created_at": "2026-10-01T10:00:00Z",
    "plan_approved": true,
    "status": "in_progress",
    "status_name": "В работе",
    "total_stages": 3,
    "completed_stages": 1,
    "progress_percent": 33.33,
    "is_overdue": false
  }]
}
```

`summary` и `total_matching` относятся ко всему разрешенному набору после всех
фильтров, до пагинации; `items` — только упорядоченная по `project_id` страница.
Смещение за пределы выборки возвращает пустой `items`, сохраняя агрегаты.
Для нулевого числа этапов прогресс равен `null`.

Статус и русская метка совпадают с `/projects/{project_id}/status`.
Приоритет правил: планирование (план не утвержден **или** этапов нет), затем
`completed`, `revision`, `under_review` и `in_progress`. Прогресс —
`completed_stages / total_stages * 100`, с округлением до двух знаков.

Этап считается просроченным, когда его статус не `completed` и
`generated_at > due_at` (строгое сравнение). Проект просрочен, если имеет хотя
бы один такой этап; поздно завершенный этап сам по себе просрочку не создает.
Один `generated_at` задает временную ссылку для всех строк и агрегатов ответа.

## Запросы и согласованность

Чтение использует только `projects`, `topics` и агрегаты `stages`; материалы и
файлы не загружаются. Запрос параметризован и одним SQL-выражением применяет
область доступа, фильтры идентификаторов/дат, статус и просрочку, затем считает
общие агрегаты и страницу. Поэтому статусные и временные фильтры применяются до
пагинации, а JOIN не размножает счетчики. Операция работает в read-only
транзакции `REPEATABLE READ`; страница и сводка используют один SQL-снимок.
Статусная приоритизация вынесена в общую вспомогательную логику `planning.py`,
которую используют и endpoint состояния, и SQL отчетности.

Безопасная проверка с полученным JWT:

```console
curl -H "Authorization: Bearer <TEST_OR_LOCAL_TOKEN>" "http://127.0.0.1:8000/reports/projects?status=in_progress&limit=10"
curl -H "Authorization: Bearer <TEST_OR_LOCAL_TOKEN>" "http://127.0.0.1:8000/reports/projects?created_from=2026-01-01T00:00:00%2B03:00&overdue_only=true"
```

Для воспроизводимых интеграционных проверок запускайте
`python -m pytest tests -v`; PostgreSQL и JWT создаются fixtures изолированно. См. также
[README_tests_RU.md](README_tests_RU.md). Тесты сверяют отчет с PostgreSQL и
существующим endpoint состояния, а граничное время задают явно.

## Ограничения

Отчет описывает текущее состояние, не хранит снимки и не включает организационную
структуру кафедр. В данной версии нет frontend, экспорта и фоновых задач.
Проверки являются учебной интеграционной верификацией и не подтверждают
готовность системы к production.
