# Управление ролями и разрешениями

Этот блок ФЗ-10 предоставляет административное изменение назначений ролей и
набора разрешений роли. Каталог ролей и разрешений остается прежним: API не
создает и не удаляет их. Выбранные ниже ограничения являются политикой этой
реализации, а не дополнительными требованиями, приписываемыми заданию.

## API

Все новые маршруты требуют действующий JWT, активную учетную запись, роль
`admin` и разрешение `roles.manage`. Проверка выполняется и при аутентификации,
и повторно в транзакции после общего блокирования административных изменений.
Наличие одного только `roles.manage` недостаточно. Для этих новых маршрутов
студент, руководитель, преподаватель, кафедра и вспомогательные роли доступа
не получают. Существующий `GET /admin/roles` сохраняет прежний контракт.

```http
GET /admin/permissions
GET /admin/roles/teacher/permissions
GET /admin/users/123/roles
```

Чтение возвращает соответственно каталог `{code, name}`, объект
`{role_code, permission_codes}` или `{user_id, role_codes}`.

Полная замена набора разрешений роли:

```http
PUT /admin/roles/teacher/permissions
Content-Type: application/json

{"permission_codes": ["projects.read", "statuses.read"]}
```

Полная замена ролей пользователя:

```http
PUT /admin/users/123/roles
Content-Type: application/json

{"role_codes": ["student", "supervisor"]}
```

В телах допустимы только объявленные поля. Коды обрезаются по краям;
пустые, повторяющиеся после нормализации и неизвестные коды отклоняются.
Пустой набор ролей пользователя запрещен. Пустой набор разрешений
академической роли допустим. Пользовательский ID ограничен положительным
диапазоном bigint. Неизвестная роль в маршруте и отсутствующий пользователь
дают 404; неизвестные коды в теле — 422; попытка выйти за политику роли — 422;
нарушение административной целостности — 409.

## Политика разрешений

Допустимое множество каждой роли ограничено матрицей, заложенной в исходной
схеме:

| Роль | Разрешения, которые можно оставить или восстановить |
|---|---|
| `student` | `projects.create`, `projects.read`, `plans.propose`, `materials.upload`, `statuses.read` |
| `supervisor` | `projects.read`, `plans.propose`, `plans.approve`, `reviews.write`, `statuses.read` |
| `teacher` | `topics.manage`, `projects.create`, `projects.read`, `supervisors.assign`, `plans.propose`, `plans.approve`, `reviews.write`, `statuses.read`, `reports.read` |
| `department` | `topics.manage`, `projects.read`, `supervisors.assign`, `statuses.read`, `reports.read` |
| `admin` | `users.manage`, `roles.manage` |

Разрешения нельзя переносить между академическими ролями. Административные
разрешения существуют только у `admin`, и эта роль всегда сохраняет оба
`users.manage` и `roles.manage`. Академические разрешения роли `admin`
добавлять нельзя. Управляются только пять штатных ролей приложения; другие
существующие коды ролей не становятся административными объектами этого API.

## Роли пользователя и проекты

Пользователь может иметь несколько ролей; его действующие разрешения —
объединение разрешений этих ролей. Активным и неактивным пользователям можно
заменять набор ролей, но администратор не может менять собственные роли.
Повтор точного набора возвращает 200 без нового аудита.

Нельзя снять `student`, `teacher` или `supervisor`, если пользователь уже
связан с проектом соответственно как студент, преподаватель или руководитель.
Возвращается 409; проекты и назначения автоматически не переназначаются.
Для снятия такой роли требуется отдельная процедура. Эти проверки применяются
и при наличии у пользователя глобальных разрешений: разрешения не отменяют
проверки участия в проектах.

## Административная целостность и блокировки

Должен оставаться хотя бы один активный пользователь с ролью `admin`.
Нельзя отключить последнего активного администратора и нельзя удалить его роль
или административные разрешения. Самоотключение администратора остается
запрещенным.

Изменения состояния учетной записи, назначений ролей и разрешений роли
используют один транзакционный PostgreSQL advisory lock (тот же ключ, что и
утилита первоначального создания администратора). Единый порядок: общий lock,
повторная проверка активного актера и его текущих полномочий, затем блокировка
строки целевого пользователя или роли и изменение данных. `create_user` и
`scripts/create_admin.py` также участвуют в этом протоколе, поскольку могут
создать назначение роли admin. Это сериализует конкурирующие операции, которые
могли бы отозвать последнее полномочие или убрать последнего активного
администратора, и избегает обратного порядка блокировок между ними.

## Аудит и JWT

Изменение таблиц `user_roles` или `role_permissions` и событие
`public.audit_events` записываются в одной транзакции. Аудит содержит актера,
действие, объект, отсортированные наборы до и после, добавленные и снятые
значения. Идемпотентный запрос не создает события; отказ не сохраняет частичные
изменения. Пароли, хеши, JWT, заголовки авторизации и параметры PostgreSQL в
аудит не записываются. Уведомления не создаются.

JWT не меняется и не кэширует разрешения: при следующем запросе активность,
роли и эффективные разрешения снова читаются из PostgreSQL. Поэтому снятие
разрешения или роли действует на последующую проверку того же JWT, а
восстановление снова разрешает операцию. Отключенная учетная запись остается
недоступной. Запрос, который уже завершил проверку до изменения, задним числом
не отзывается.

## Проверки

Требуются Python 3.13, зависимости `requirements-test.txt` и Docker либо
установленные PostgreSQL 17 `initdb`/`postgres`. Запуск из корня репозитория:

```console
python -m pip install -r requirements-test.txt
python -m scripts.test_materials_unit
python -m pytest tests -v --postgres-backend=docker
```

На Windows с установленными бинарными файлами PostgreSQL:

```console
python -m pytest tests -v --postgres-backend=native --pg-bin="C:\Program Files\PostgreSQL\17\bin"
```

Fixture создает собственный PostgreSQL и временное хранилище, не читает
настоящий `.env`, не подключается к пользовательской базе и не использует
`uploads/`. Интеграции проверяют авторизацию, политику, эффективные разрешения
с тем же JWT, аудит, возврат к исходной матрице прав и конкурентные изменения
под управляемой синхронизацией с ограниченным временем ожидания. Workflow
`Backend tests` автоматически собирает `pytest tests`.

Ограничения: изменения действуют только на пять штатных ролей; управление
каталогом ролей/разрешений, удаление учетных записей, отзыв JWT и автоматическое
переназначение участников проекта не реализуются. Тесты не проверяют внешние
системы и не являются подтверждением готовности к production.
