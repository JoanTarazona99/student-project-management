# Проверки backend

Учебные интеграционные тесты используют настоящий PostgreSQL 17, FastAPI
TestClient, SQLAlchemy и psycopg. Правила приложения и SQL-схема не изменены.

## Требования и запуск

Нужны Python 3.13, зависимости проекта и работающий Docker с Linux-контейнерами:

```console
python -m pip install -r requirements-test.txt
python -m playwright install chromium
python -m scripts.test_materials_unit
python -m pytest tests -v
```

В Windows команды выполняются в активированном виртуальном окружении.
Без Docker можно использовать установленные **бинарные файлы** PostgreSQL
(не запущенную рабочую службу):

```console
python -m pytest tests -v --postgres-backend=native --pg-bin="C:\Program Files\PostgreSQL\17\bin"
```

На Linux `initdb` и `postgres` должны быть в PATH либо в каталоге `--pg-bin`.
Нативный PostgreSQL нельзя запускать от root. Отсутствие PostgreSQL, Docker или
ошибка подключения приводят к ошибке тестов, а не к skip.
Отдельный сценарий можно выбрать через `python -m pytest tests -v -k complete_three_stage`.

## Изоляция и конфигурация

Внешний DSN не принимается. Не задавайте параметры рабочей БД: тесты их не
используют и не открывают настоящий `.env`. До импорта `app.main` fixture
перехватывает только `dotenv.dotenv_values`, возвращая тестовую конфигурацию.
Engine, авторизация, SQL и обработчики не подменяются. Повторное использование
уже импортированного `app.database` запрещено.

- По умолчанию fixture сама создает контейнер `postgres:17` с уникальным именем,
  временной БД в tmpfs и случайным портом, доступным только через 127.0.0.1.
  Нет bind mount, постоянного volume и подключения к рабочему PostgreSQL.
- В режиме native `initdb` создает новый кластер в системном временном каталоге,
  затем запускается собственный дочерний процесс на случайном порту с
  SCRAM-аутентификацией. Завершается только этот процесс.
- Внутри своего сервера создаются `student_projects` и `spm_dev`; исходный
  `database/01_schema_student_projects.sql` выполняется без изменений и с
  сохранением всех защит. Эти имена сами по себе **не** подтверждают изоляцию:
  ее обеспечивает создание сервера fixture. DROP DATABASE/SCHEMA не применяется.
- `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` и `JWT_SECRET`
  генерируются fixture, а не читаются из окружения или `.env`. Пароль БД и JWT
  случайные для каждого запуска. Пароли созданных пользователей только тестовые.
- `UPLOAD_ROOT` заменяется на отдельный `TemporaryDirectory` каждой проверки; реальный
  `uploads/` не используется. `MAX_BYTES` не меняется: проверяется превышение
  действительного лимита 20 МиБ.
- SQL создает штатные роли и разрешения. Каждый тест создает собственных
  пользователей и назначения ролей, затем через API — темы, два проекта и план.
  ID получаются из ответов и RETURNING, не предполагаются заранее.
  Данные не очищаются между тестами: уникальные пользователи и проекты исключают
  зависимость от порядка. Сервер и временное хранилище удаляются после запуска.

Запускайте pytest отдельным процессом. Принудительное завершение процесса или
машины может помешать финализации временных ресурсов; не очищайте рабочую БД
или `uploads/` для устранения такой ситуации.

## CI и покрытие

Workflow `.github/workflows/backend-tests.yml` выполняется для PR в main,
push и вручную через Actions → Backend tests → Run workflow.
Он устанавливает закрепленные зависимости, проверяет Docker, загружает
PostgreSQL и тестовый Chromium с зависимостями ОС, выполняет 14 прежних
unit-тестов, интеграционные и настоящие браузерные тесты.
Runner закреплен на `ubuntu-24.04` для совместимости с закрепленным Playwright;
`ubuntu-latest` с Ubuntu 26.04 этой версией пока не поддерживается.
Секреты GitHub, рабочий `.env` и компьютер пользователя не нужны.

Проверяются авторизация и скрытие чужих ресурсов (401/403/404), утверждение
плана, конфликты без побочных изменений, файлы и история версий, решения,
уведомления и полный проход трех этапов с прогрессом 33.33/66.67/100.
Плановые даты находятся в 2099 году: работа над открытым этапом не требует
ожидания starts_at. Снимки БД, аудита, уведомлений и файлов проверяют отсутствие
побочных изменений при отказах и повторных действиях.
Дополнительно проверяются редактирование учетных записей, разрешение
`users.manage`, аудит, отключение/повторная активация и параллельная защита
последнего активного администратора. См. [README_user_management_RU.md](./README_user_management_RU.md).
Администрирование ролей и разрешений покрывается отдельной интеграционной
группой: фиксированная политика ролей, действия с тем же JWT, полный аудит,
восстановление исходной матрицы разрешений и управляемые конкурентные запросы.
Подробности API приведены в [README_roles_permissions_RU.md](./README_roles_permissions_RU.md).
Проверка сроков покрывает границы UTC, уникальных активных адресатов, дедупликацию,
симуляцию, аудит и rollback, CLI, ограниченное ожидание блокировок и конкуренцию
с реальным принятием этапа. См. [README_deadlines_RU.md](./README_deadlines_RU.md).
Для повторения всей интеграции в обратном порядке добавьте `--reverse-order`
к той же команде pytest. Исходные assertions остальных модулей не изменены.
Авторизованные изменения дат утвержденного плана покрываются новым модулем:
полный набор этапов, ожидаемые даты и конфликты, неизменность completed,
сохранение материалов и состояний, аудит/уведомления, rollback и гонки
с принятием/генерацией сроков. См. [README_plan_dates_RU.md](./README_plan_dates_RU.md).
Минимальный web-интерфейс проверяется отдельно через HTTP и Playwright Chromium:
вход, действительные права, данные/фильтры/загрузка, уведомления, ошибки, смена
сессии, безопасный DOM и узкий экран. HTTP-сервер, браузер и файлы принадлежат
fixtures, не пользователю. См. [README_web_ui_RU.md](./README_web_ui_RU.md).
Для только браузерных проверок: `python -m pytest tests/test_web_ui_browser.py -v`
с теми же параметрами PostgreSQL. Отсутствие Chromium — ошибка, не skip.

Для отдельной защиты «только последняя ожидающая версия» создается SQL-допустимое
состояние с двумя непроверенными версиями: штатный API сам не позволяет его
получить. Остальной жизненный цикл выполняется через API.

## Ограничения

Кроме проверенной гонки генерации уведомлений с принятием этапа, пока не проверяются
прочие конкурентные запросы к академическим операциям, авария во время
commit, недоступность БД/диска, восстановление orphan files и истечение/отзыв JWT.
Проверки PDF/DOCX используют минимальные
признаки формата, которые принимает
существующий обработчик, а не проверку полноценного документа в офисном ПО.
Параллельный запуск через pytest-xdist не настроен.
Контейнер закреплен на основной версии PostgreSQL 17, не на digest образа.
Starlette 1.10.0 предупреждает об устаревании httpx в TestClient. Зависимости
приложения не обновляются ради устранения этого предупреждения; тесты используют
совместимый httpx 0.28.1.

Это не подтверждение готовности к production. Multipart разбирается до проверки
лимита обработчиком; нужны внешние ограничения тела запроса и объема хранилища.
PostgreSQL и файловая система не имеют общей атомарной транзакции, поэтому
аварийные ситуации могут оставлять файлы без записей.
